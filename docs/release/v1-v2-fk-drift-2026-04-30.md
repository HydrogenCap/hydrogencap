## 0. Headline finding — bigger than expected

The V1 and V2 id spaces are **almost completely disjoint**. We probed every V1/V2 sibling pair for shared primary keys:

| Pair | V1 rows | V2 rows | Shared id |

| `companies` ↔ `legal_entities` | 19 | 22 | **0** |
| `tenants` ↔ `tenants_v2` | 3 | 3 | **0** |
| `rooms` ↔ `rooms_v2` | 17 | 23 | (not shared — see note) |
| `share_classes` ↔ `share_classes_v2` | 19 | 19 | (not shared — see note) |
| `compliance_documents` ↔ `compliance_documents_v2` | 117 | 140 | (not shared — see note) |

**Implication:** the prompt's "safe-bucket" assumption — that some FKs can be re-pointed mechanically because every current V2 row already has a V1 mirror — is **false in this database**. Every drift-prone FK either has live V1-only rows that would orphan on a naive constraint swap, or needs a per-row remap (V1 id → V2 id, by address/postcode/name) before the swap is safe.

## 5. Per-FK detail blocks

### 5.1 `properties_v2.legal_owner_company_id → companies.id` *(Class A, drift-prone)*

```sql
-- Current
ALTER TABLE public.properties_v2
  DROP CONSTRAINT properties_v2_legal_owner_company_id_fkey;

-- Target (after remapping all 21 populated rows: companies.id → legal_entities.id)
ALTER TABLE public.properties_v2
  ADD CONSTRAINT properties_v2_legal_owner_company_id_fkey
  FOREIGN KEY (legal_owner_company_id)
  REFERENCES public.legal_entities(id)
  ON DELETE SET NULL;
```

- **Blast radius (no remap):** `ALTER` aborts; 21 rows fail FK validation.
- **Blast radius (with remap):** owners now resolve correctly to `legal_entities`. No cascading delete change (`SET NULL` preserved).
- **RLS impact:** none — `legal_owner_company_id` is not referenced in any policy `qual` / `with_check`.
- **Remap strategy:** join `companies` to `legal_entities` on `companies_house_number` (where present) and fall back to normalised `legal_name`. Manually resolve unmatched rows before constraint swap.

## Trigger audit script — locks in #99 ground-truth-grep lesson — 2026-05-10

Lesson from #99 (Rooms §0b Ship E no-op): we relied on conversational memory of "which V1 tables already have `v1_freeze_guard`". Memory was stale (4-of-6 cited; actual 3-of-6). To prevent recurrence, drift between intent and reality is now a CI failure.

### Approach: static parsing of `supabase/migrations/*.sql`

`scripts/check-freeze-trigger-coverage.mjs` walks migration files in chronological filename order and replays trigger events to compute a final per-table install state:

- **Install pattern A** (seed migration `20260428235107`): `FOREACH tbl IN ARRAY ARRAY['properties','rooms','tenants'] LOOP … format('CREATE TRIGGER v1_freeze_guard … ON public.%I', tbl)`. Detected by matching the loop header + a `CREATE TRIGGER v1_freeze_guard` reference in the body.
- **Install pattern B** (single-table DO blocks for loans/costs/income/tenancies): `CREATE TRIGGER v1_freeze_guard … ON public.<table>`. Detected by literal `public.\w+` match — `format()`-wrapped CREATEs containing `public.%I` are intentionally excluded.
- **Drop pattern**: `DROP TRIGGER IF EXISTS v1_freeze_guard ON public.<table>`. Same `public.\w+` literal requirement excludes the `format()`-wrapped DROP-then-CREATE precursor inside the seed loop.

A drop+create pair in the same file is treated as a net install. Final state is replayed sequentially across all migrations.

### Config file shape

`scripts/v1-freeze-trigger-config.json` lists the 6 §0b V1 tables across two arrays, each entry carrying a `reason` for inline context:

- `expected_installed`: `properties`, `rooms`, `tenants` — installed via the 2026-04-28 seed migration.
- `pending_install`: `share_classes`, `compliance_items`, `compliance_documents` — each pending its respective §0b Ship C atomic write+read+realtime flip before Ship E can install the trigger.

The script asserts the config covers the §0b set exactly (no gaps, no duplicates, no out-of-set entries) and that final migration state matches each entry's bucket.

### Vitest self-test

`src/__tests__/check-freeze-trigger-coverage.test.ts` stages sandbox migration trees and asserts:

1. Clean tree (seed installs match `expected_installed`, no drift) → exit 0.
2. Unexpected install on a `pending_install` table (`share_classes`) → exit 1, error names the table.
3. Drop of an `expected_installed` table (`properties`) → exit 1, error names the table.

### Wiring

- `package.json` adds `check:freeze-triggers` and appends it to `verify` immediately after `check:no-v1-refs` — the two §0b lock-in guards run consecutively.
- CI runs `npm run lint`, `check:no-any-disables`, `check:no-v1-refs`, `check:freeze-triggers`, `typecheck`, `vitest`, `build`, `check:edge` (70/70). All green at ship time.

### Forward mechanism

When share_classes / compliance_items / compliance_documents §0b Ship C lands, the accompanying Ship E migration installs `CREATE TRIGGER v1_freeze_guard … ON public.<table>` (pattern B). The next CI run will then fail with `pending table '<table>' has v1_freeze_guard installed in <migration> — move it from pending_install to expected_installed`. The config update is part of that ship's PR; CI re-passes once the entry moves buckets. No silent drift possible.

### Lesson encoded

Trigger install state is now derived from migration history rather than chat memory. Any future §0b E-step authoring a non-`CREATE TRIGGER`-shaped install (e.g. a plpgsql DO block hiding the install inside a `format()` template outside the FOREACH-ARRAY pattern) will silently miss this parser — the script's header docstring flags this as the known fallback case requiring either a new detection branch or DB-query Option B.

## Verify-chain resilience — deno.land 500 flake closed — 2026-05-10

### Motivation

Rooms §0b Ship E (#94 follow-up) hit a transient `check:edge` failure tonight: `deno check supabase/functions/admin-stats/index.ts` failed fetching a `deno.land/std` dependency (HTTP 5xx from the registry, not a code/type issue). Re-running the same command without changes passed. Real CI risk during deno.land outages.

### Option chosen — A (retry wrapper)

Picked Option A over Option B (`--vendor`) because:

- **Smaller blast radius** — wrapper is ~60 LOC, leaves `check-edge-functions.mjs` untouched. Vendor would add an MB-scale `vendor/` dir to repo clone + a bootstrap step + cache-invalidation rules to maintain.
- **No new failure mode at clone time** — vendor populate would itself need network on first run (chicken-and-egg in CI on a cold clone with deno.land down); the wrapper degrades gracefully on every run, not just non-cold ones.
- **Conservative matcher set** — see below; only network-shaped failures retry. Real type/lint errors fail-fast.

### Implementation

- `scripts/run-with-retry.mjs` — generic wrapper. Spawns the child, captures combined stdout+stderr, retries on `code !== 0 && isTransient(output)`. Exponential backoff (5s / 15s / 45s), 3 attempts max, exits with the final attempt's code.
- `package.json` — `check:edge` now invokes `node scripts/run-with-retry.mjs --max=3 --backoff=5000,15000,45000 -- node scripts/check-edge-functions.mjs`. Verify chain unchanged.

### Transient-error matcher set

```
/fetch.*deno\.land/i
/deno\.land.*\b5\d{2}\b/i
/\b(ECONNRESET|ETIMEDOUT|EAI_AGAIN|ENOTFOUND|ECONNREFUSED)\b/
/error sending request/i
/connection (closed|reset) before message completed/i
/tcp connect error/i
```

Deliberately narrow. Confirmed by self-test that the following do **not** match (i.e. fail-fast as intended): `TS2345 Argument of type ...`, `TypeError: x.y is not a function`, `AssertionError`. No retry mask over real errors.

### Self-test

`src/__tests__/run-with-retry.test.ts` (5 cases):

1. `TRANSIENT_PATTERNS` matches deno.land 5xx, ECONNRESET, ENOTFOUND.
2. Type errors / TypeErrors / AssertionErrors are NOT classified transient.
3. Two transient failures then success → exits 0 after 3rd attempt.
4. Three transient failures → exits with last code (non-zero).
5. Non-transient error on first attempt → exits immediately, no retry.

All passing.

### Trade-off documented

A retry wrapper hides slow-but-eventually-passing CI: a deno.land degradation that adds ~60s of retry-then-success won't surface as a red build, only as a slower one. Acceptable trade vs. the hard-fail today. If retry-wrapping starts masking a sustained registry issue, watch for `[run-with-retry] transient failure detected` lines in CI logs — their frequency is the signal to reconsider Option B.

### Lesson encoded

Verify-chain commands that touch external registries (deno.land, npm, esm.sh) are intrinsically flaky. The `run-with-retry.mjs` wrapper is general-purpose; future commands with the same shape (e.g. a hypothetical `check:typeshed` or `check:peer-deps`) can wrap themselves the same way without re-implementing the matcher.

### run-with-retry transient matchers — hardening pass — 2026-05-12

Tightened `scripts/run-with-retry.mjs` to defend against false-positive retries when a real bug's stack trace or vitest assertion diff happens to contain a transient-shaped substring (e.g. an `AssertionError` whose diff contains the literal `ETIMEDOUT`).

**Matcher rationale (now inline-documented in the script):**

| Pattern | Why safe | False-positive risk | Fixture |
|---|---|---|---|
| `/fetch.*deno\.land/i` | Only emitted by Deno import resolution | TS source w/ deno.land in comment + TypeError upstream | `error: error sending request for url (https://deno.land/...)` |
| `/deno\.land.*\b5\d{2}\b/i` | HTTP 5xx is by definition transient | Assertion diff containing literal "5xx" | `deno.land returned 502 Bad Gateway` |
| `/\b(ECONNRESET\|ETIMEDOUT\|EAI_AGAIN\|ENOTFOUND\|ECONNREFUSED)\b/` | Kernel-level transient socket errors; word-boundary anchored | Vitest diff that asserts on a socket code string | `Error: connect ECONNRESET 1.2.3.4:443` |
| `/error sending request/i` | Reqwest/Deno transport-failure phrase | Low — phrase is not a typical app idiom | `error: error sending request for url` |
| `/connection (closed\|reset) before message completed/i` | HTTP/2 mid-flight reset | Low — phrase is HTTP-stack specific | `connection closed before message completed` |
| `/tcp connect error/i` | TCP handshake failure | Low — phrase is network-stack specific | `tcp connect error: connection refused` |

**Fail-fast precedence (new):** `FAIL_FAST_PATTERNS` always wins over `TRANSIENT_PATTERNS`. If output contains any of:

- `error: TypeError` / bare `TypeError:`
- `AssertionError:` / `SyntaxError:` / `ReferenceError:`
- `TS\d{4}:` (tsc diagnostic codes) or `error TS\d{4}` (tsc CLI form)
- ` FAIL  …test.ts` (vitest failure header)
- `Expected: …Received:` (jest/vitest assertion diff block)

…the run is treated as a real bug and exits immediately, even if a transient pattern also matched. Prevents a TypeError stack containing `https://deno.land/...` or an assertion diff containing `ECONNRESET`/`5xx` from triggering a spurious retry.

**New tests** (`src/__tests__/run-with-retry.test.ts`, 11 cases total, +6 hardening cases):

- `hasFailFast catches all known real-bug shapes`
- `TypeError mentioning deno.land in stack trace → NOT transient`
- `AssertionError diff containing ETIMEDOUT literal → NOT transient`
- `vitest assertion against "5xx" string literal → NOT transient`
- `exits immediately when output has BOTH transient + fail-fast pattern (1 attempt)`
- `exits immediately when vitest FAIL contains ECONNRESET in diff`

**Matchers narrowed/tightened:** none retired. The audit confirmed all 6 transient patterns remain genuinely network-shaped; the fix was the precedence rule, not the patterns themselves. Existing transient-only tests still pass unchanged — the layer is additive, not subtractive.

**Cost:** one extra `FAIL_FAST_PATTERNS.some(...)` pass per failed attempt (≪1ms), zero impact on success path.

## CI V2 reference guard SQL expansion (Option 1 — asymmetric lists) — 2026-05-12

Closed the open #104 blocker by shipping the asymmetric SQL/TS guard design.

### Asymmetric design
`scripts/check-no-v1-table-refs.mjs` now scans two file classes with two
different V1 lists, by deliberate intent:

- **TS/JS layer** (`src/`, `supabase/functions/**/*.{ts,tsx,js,jsx,mjs,cjs}`):
  full V1 list — fully-dropped §0a tables + §0b write-frozen tables + the
  renamed-away `*_v2` names. App code must touch none of these.
- **SQL layer** (`supabase/migrations/**/*.sql`, `supabase/functions/**/*.sql`):
  ONLY the 4 fully-dropped §0a tables (`SQL_FULLY_DROPPED_V1_TABLES`).

Why asymmetric: §0b tables (`properties`, `rooms`, `tenants`,
`share_classes`, `compliance_items`, `compliance_documents`) still live in
the DB and are referenced by historical migrations and current RLS / index
migrations. Flagging them in SQL would force ~89 allowlist markers on
legitimate, baked-in DB history. App code is the ratchet — SQL catches the
narrower "can't ever legitimately reappear" case.

### SQL-flagged tables
`loans`, `tenancies`, `costs`, `income` — all dropped, all replaced by
`loan_facilities`, `tenancy_agreements`, `property_cost_budgets`,
`property_income_budgets` respectively. SQL patterns matched
case-insensitively, with word boundaries: `FROM`, `UPDATE`,
`INSERT INTO`, `DELETE FROM`, `REFERENCES`, `JOIN` against optionally
`public.`-qualified names. Single-quoted string literals and `--` line
comments are stripped before matching to avoid false positives like
`COMMENT ON ... 'excluded from income KPIs'`.

### §0b → SQL-list migration trigger
**When a §0b table's Ship F (DROP TABLE public.<v1>) lands**, move it from
`RENAMED_V2_TABLES` (TS-only) into `SQL_FULLY_DROPPED_V1_TABLES`
(both layers). That table can then never legitimately reappear in any
file class.

### Per-file allowlist marker
`-- @allow-v1-refs: <reason>` (SQL) or `// @allow-v1-refs: <reason>` (TS)
on any line in a file disables the guard for that file. Used to mark the
28 pre-cutover historical migrations that legitimately reference §0a
tables (RLS/policies/cleanup migrations baked into DB history). Should
rarely be needed for new SQL — the 4 SQL-flagged tables shouldn't appear
in new code.

### Closed gap
Anyone re-creating `public.loans` (etc.) in a new migration now fails CI
on the SQL layer, not just on TS imports. Verify chain green: lint,
check:no-any-disables, check:no-v1-refs (TS + SQL),
check:freeze-triggers, vitest, check:edge, check:retry-wrapper.

### #104 SQL guard polish trio — 2026-05-12

Three hardening items shipped together against `scripts/check-no-v1-table-refs.mjs`:

**A. More SQL pattern tests** — added vitest fixtures covering every
verb in the SQL pattern set: `UPDATE public.loans`, `INSERT INTO
public.loans`, `DELETE FROM loans` (no `public.` prefix), and
`REFERENCES public.tenancies` (FK-creation form). Each asserts exit 1
and the offending table name in stderr.

**B. Multi-line SQL** — replaced the per-line SQL scan with a
whole-file scan via the new `scanSqlContent(content)` helper. The
existing `\s+` segment in the regex already crosses newlines, so
statements like `SELECT *\nFROM\n  public.loans\nWHERE ...` are now
caught. Line numbers are recovered by counting newlines up to the
match index, so error output remains precise. New fixture asserts
the multi-line case.

**C. Tightened string-literal stripping** — the previous one-liner
regex (`/'(?:[^']|'')*'/g` + `/--.*$/`) couldn't handle PostgreSQL's
`E'...'` escape strings, `$$...$$` / `$tag$...$tag$` dollar quotes,
or `/* ... */` block comments. Replaced with a tokenizer-style
`stripSqlNoise(s)` pass that walks the content once and blanks each
noise span (preserving newlines so byte offsets stay aligned with
line numbers). Five new fixtures exercise each construct, plus a
"mixed" fixture confirming a real `FROM public.loans` after a
stripped string literal on the same line still flags.

**Sweep** — `npm run check:no-v1-refs` against the full repo:
exit 0, no false positives, no false negatives. Verify chain remains
green. Vitest count: 6 → 16 (+10 new SQL fixtures).
