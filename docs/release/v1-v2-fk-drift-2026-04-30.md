**Generated:** 2026-04-30
**Mode:** read-only inventory (no migrations written, no source touched)
**Scope:** every FK in `public` whose constraint table belongs to the V2 era (`*_v2`, `legal_entities`) **or** is V-neutral but still references a V1 table that has a V2 sibling.

## 0. Headline finding — bigger than expected

The V1 and V2 id spaces are **almost completely disjoint**. We probed every V1/V2 sibling pair for shared primary keys:

| Pair | V1 rows | V2 rows | Shared id |
|---|---:|---:|---:|
| `properties` ↔ `properties_v2` | 25 | 27 | **1** (the shadow row hand-inserted on 2026-04-30 for 24 West Street) |
| `companies` ↔ `legal_entities` | 19 | 22 | **0** |
| `tenants` ↔ `tenants_v2` | 3 | 3 | **0** |
| `rooms` ↔ `rooms_v2` | 17 | 23 | (not shared — see note) |
| `share_classes` ↔ `share_classes_v2` | 19 | 19 | (not shared — see note) |
| `compliance_documents` ↔ `compliance_documents_v2` | 117 | 140 | (not shared — see note) |

**Implication:** the prompt's "safe-bucket" assumption — that some FKs can be re-pointed mechanically because every current V2 row already has a V1 mirror — is **false in this database**. Every drift-prone FK either has live V1-only rows that would orphan on a naive constraint swap, or needs a per-row remap (V1 id → V2 id, by address/postcode/name) before the swap is safe.

- **Safe bucket (re-point with no data movement):** **none.** The disjoint id spaces mean every drift-prone FK has live rows on the V1 side that don't exist on the V2 side.

Each needs a paired remap table (V1 id → V2 id, by address/postcode for properties, by name + companies-house number for companies, by name + email for tenants) **before** the constraint swap. Cannot be batched.

## 4. RLS rewrite scope

A search of `pg_policies` for substrings matching V1 table names found **dependent policies on these tables**, every one of which currently joins through a V1 referent and would need rewriting in lockstep with the FK swap (drop + recreate inside the same transaction, otherwise RLS will deny all reads mid-flight):

**Touch-V1-`properties` (re-point to `properties_v2`):**
`costs` (4 policies), `floorplans` (4), `go_live_checklists` (3), `income` (4), `insurance_policies` (5), `loans` (4), `passport_autofill_suggestions` (4), `passport_field_audit` (2), `photos` (5), `property_beneficial_owners` (4), `property_legal_ownership` (4), `property_ownership` (4), `property_passport` (4), `property_title_numbers` (4) — **~57 policies**.

**Touch-V1-`companies` (re-point to `legal_entities`):**
`company_metric_snapshots` (4), `ownership_links` (4), `shareholdings` (4) — **~12 policies**.

**Touch V1-`tenants` / V1-`rooms` / V1-`share_classes` / V1-`compliance_documents`:** none of the referencing tables (maintenance_requests, tenant_portal_*, document_share_links) currently have V1-name joins in their policies, so RLS rewrites for those would be small or zero.

The cosmetic-bucket migration described in §3 has **no RLS impact** — those 8 FKs have zero referencing rows and the dependent tables either have no V1-name joins in their policies (`tenant_portal_*`, `document_share_links`, `maintenance_requests`) or have policies that join through `org_id` / membership functions rather than through the V1 table directly.

## 5. Per-FK detail blocks

### 5.1 `properties_v2.legal_owner_company_id → companies.id` *(Class A, drift-prone)*

```sql
-- Current
ALTER TABLE public.properties_v2
  DROP CONSTRAINT properties_v2_legal_owner_company_id_fkey;

-- Target (after remapping all 21 populated rows: companies.id → legal_entities.id)
ALTER TABLE public.properties_v2
  ADD CONSTRAINT properties_v2_legal_owner_company_id_fkey
  FOREIGN KEY (legal_owner_company_id)
  REFERENCES public.legal_entities(id)
  ON DELETE SET NULL;
```

- **Blast radius (no remap):** `ALTER` aborts; 21 rows fail FK validation.
- **Blast radius (with remap):** owners now resolve correctly to `legal_entities`. No cascading delete change (`SET NULL` preserved).
- **RLS impact:** none — `legal_owner_company_id` is not referenced in any policy `qual` / `with_check`.
- **Remap strategy:** join `companies` to `legal_entities` on `companies_house_number` (where present) and fall back to normalised `legal_name`. Manually resolve unmatched rows before constraint swap.

## 6. Final recommendation (what to do next)

**Ship the cosmetic bucket first** as a single Build-mode migration prompt — 8 FKs, zero rows touched, zero RLS rewrites, pure constraint swap, plugs the leak. Then **handle each drift-prone FK individually** with a paired remap table — start with `properties_v2.legal_owner_company_id` (smallest blast radius, 21 rows, well-bounded `companies → legal_entities` map by `companies_house_number` then `legal_name`), and only attempt the heavy hitters (`documents.property_id` / `property_passport.property_id` — 179 + 24 rows plus a 57-policy RLS rewrite) once the smaller drift-prone cases have validated the remap procedure end to end.
