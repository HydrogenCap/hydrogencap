## Section C — Policies with `true` / true-equivalent expressions

The DB scan found **9** policies whose `USING` or `WITH CHECK` is literally `true`, `auth.uid() IS NOT NULL`, or `auth.role() IS NOT NULL`. Classification below.

### C.1 — Intentionally public / global reference reads — **leave as-is, add documenting comment**

| Table | Cmd | Policy | Expression | Rationale |
|---|---|---|---|---|
| `ai_extraction_templates` | SELECT | Authenticated read | `auth.uid() IS NOT NULL` | Global template library shared by all tenants. |
| `certificate_type_mappings` | SELECT | Authenticated users can read certificate type mappings | `true` | Global lookup table (cert-type → category). |
| `compliance_templates` | SELECT | Anyone authenticated can read templates | `auth.uid() IS NOT NULL` | Global compliance template catalogue. |
| `financial_categories` | SELECT | Authenticated users can read financial_categories | `auth.uid() IS NOT NULL` | Global chart-of-accounts seed data. |
| `demo_requests` | INSERT | Anyone can submit demo requests | `true` (with check) | Public marketing form; companion SELECT is admin-gated. |

➡️ **Action:** Add an `-- INTENTIONAL PUBLIC READ: <reason>` SQL comment above each policy in its source migration (or a follow-up doc-only migration) so future audits can skip them quickly. No behavioural change.

### C.2 — Service / system-write policies — **leave as-is, scope is service-role-only by convention**

| Table | Cmd | Policy | Expression | Notes |
|---|---|---|---|---|
| `audit_log` | INSERT | System can insert into audit_log | `WITH CHECK true` | Written by triggers / service role. SELECT side is correctly org-scoped. The PUBLIC role grant is fine because triggers run `SECURITY DEFINER`. Consider restricting to `TO service_role` for defence-in-depth. |
| `scheduled_email_runs` | INSERT | Service can insert email runs | `WITH CHECK true` | Written by cron / edge functions. Same defence-in-depth note. |
| `scheduled_email_runs` | UPDATE | Service can update email runs | `USING true` | Same as above. |

➡️ **Suggested hardening (optional, not required):**
```sql
-- Defence-in-depth: restrict service-only writes to the service_role grantee.
ALTER POLICY "System can insert into audit_log" ON public.audit_log TO service_role;
ALTER POLICY "Service can insert email runs"   ON public.scheduled_email_runs TO service_role;
ALTER POLICY "Service can update email runs"   ON public.scheduled_email_runs TO service_role;
```

### C.3 — Accidentally permissive — **tighten**

| Table | Cmd | Policy | Current | Risk |
|---|---|---|---|---|
| `notifications` | INSERT | Authenticated users can create notifications | `WITH CHECK (auth.uid() IS NOT NULL)` | Any authenticated user (including a tenant or shareholder portal user from a different org) can insert a row targeting any `user_id`. Spoofing / spam risk. |

➡️ **Proposed tightening (report-only — not applied):**
```sql
-- Restrict notification inserts: a user may only create a notification addressed to themselves.
DROP POLICY "Authenticated users can create notifications" ON public.notifications;

CREATE POLICY "Users can insert own notifications"
ON public.notifications
FOR INSERT
TO authenticated
WITH CHECK (
  user_id = auth.uid()
  -- system / cross-user notifications must go through SECURITY DEFINER fn or service_role
);

-- Allow service_role + SECURITY DEFINER triggers to bypass for system notifications:
CREATE POLICY "Service can insert system notifications"
ON public.notifications
FOR INSERT
TO service_role
WITH CHECK (true);
```

> No other `true`-equivalent policies in the database besides those listed above. The Supabase linter `SUPA_rls_policy_always_true` warnings (4 of them) all map to the rows in C.2 + C.3.

### Action items for edge functions

1. **`freeagent-oauth-callback`** — currently has no auth gate (expected for an OAuth callback) but the audit could not confirm the `state` value is HMAC-signed or replay-protected. **Action:** add an explicit `// PUBLIC: OAuth callback — security relies on signed state nonce + short TTL` comment, and verify in code review that the `state` token is HMAC-signed (not just base64-encoded JSON) and single-use. If it is only base64, that is a **NEEDS-HARDENING** item, not a NEEDS-AUTH one.
2. **`get-maps-key`** — the function name implies a public read but the implementation requires auth. Either rename to `get-maps-key-authed` or add a `// AUTH: requires session` comment to prevent future contributors from "fixing" it by removing the auth check.
3. No function in the audit was classified **NEEDS AUTH**.

## Section E — Recommended fix order (highest blast-radius first)

The items below are ordered by impact (rows × sensitivity × cross-tenant exposure). Only **#1** is a real cross-tenant data risk uncovered by this audit; the rest are defence-in-depth and hygiene.

| # | Area | Action | Blast radius | Effort |
|---|---|---|---|---|
| 1 | `notifications` INSERT policy (Section C.3) | Replace `auth.uid() IS NOT NULL` with `user_id = auth.uid()`; add a separate `service_role`-only policy for system notifications. | Cross-tenant spoofing of in-app alerts. | Low |
| 2 | `audit_log` + `scheduled_email_runs` service-write policies (C.2) | Restrict policies to `TO service_role` so PUBLIC-grant + `true` cannot be combined by future schema drift. | Defence-in-depth. | Low |

### Item 2 — Four `SECURITY DEFINER` views (linter ERROR 0010)

The Supabase linter flags four public views as `SECURITY DEFINER` (i.e., they run with the view-creator's privileges and bypass RLS of the querying user). Their definitions are below.

#### 2.1 `public.investor_commitment_detail`
```sql
SELECT ic.id AS commitment_id, ic.org_id, ic.investor_id, i.investor_name,
       ic.entity_id, le.entity_name, le.entity_type, ic.commitment_type,
       ic.committed_amount, ic.drawn_amount,
       ic.committed_amount - ic.drawn_amount AS undrawn_amount,
       ic.equity_percentage, ic.commitment_date, ic.maturity_date,
       ic.coupon_rate, ic.payment_frequency, ic.status,
       ic.documentation_url, ic.notes,
       (SELECT count(DISTINCT ol.subject_id) FROM companies c
          JOIN ownership_links ol ON ol.owner_party_id = c.party_id
                                 AND ol.subject_type = 'property'
                                 AND ol.effective_to IS NULL
          WHERE c.legal_name = le.entity_name AND c.org_id = le.org_id) AS property_count,
       /* + entity_total_valuation, investors_share_valuation, total_distributions_received */
  FROM investor_commitments ic
  JOIN investors i ON i.id = ic.investor_id
  JOIN legal_entities le ON le.id = ic.entity_id
 ORDER BY i.investor_name, le.entity_name;
```
**Recommendation: convert to SECURITY INVOKER.** All three base tables (`investor_commitments`, `investors`, `legal_entities`) already enforce org-scoped RLS. Running the view as the caller would correctly limit rows to the caller's org without weakening security. The `companies`/`ownership_links`/`properties` subqueries are wrapped inside the SELECT and would also resolve correctly under invoker RLS for any authenticated portfolio user.

#### 2.2 `public.investor_portfolio_summary`
```sql
SELECT i.id AS investor_id, i.org_id, i.investor_name, i.investor_type, i.email,
       i.portal_access_enabled,
       count(DISTINCT ic.entity_id) AS entities_invested,
       count(DISTINCT ic.id) AS total_commitments,
       COALESCE(sum(ic.committed_amount),0) AS total_committed,
       COALESCE(sum(ic.drawn_amount),0)    AS total_drawn,
       COALESCE(sum(ic.committed_amount)-sum(ic.drawn_amount),0) AS total_undrawn,
       COALESCE(dist.total_distributed,0)  AS total_distributed,
       /* + dividend / interest / capital-return splits and distribution_multiple */
  FROM investors i
  LEFT JOIN investor_commitments ic
         ON ic.investor_id = i.id
        AND ic.status IN ('active','fully_drawn')
  LEFT JOIN LATERAL (
    SELECT id2.investor_id,
           sum(id2.amount) AS total_distributed,
           sum(id2.amount) FILTER (WHERE id2.distribution_type='dividend')        AS total_dividends,
           sum(id2.amount) FILTER (WHERE id2.distribution_type='interest')        AS total_interest,
           sum(id2.amount) FILTER (WHERE id2.distribution_type IN ('capital_return','loan_repayment')) AS total_capital_returned
      FROM investor_distributions id2
     WHERE id2.investor_id = i.id AND id2.status='paid'
     GROUP BY id2.investor_id
  ) dist ON true
  GROUP BY i.id, i.org_id, i.investor_name, i.investor_type, i.email,
           i.portal_access_enabled, dist.total_distributed,
           dist.total_dividends, dist.total_interest, dist.total_capital_returned;
```
**Recommendation: convert to SECURITY INVOKER.** All base tables (`investors`, `investor_commitments`, `investor_distributions`) carry org-scoped RLS, so invoker semantics naturally restrict rows to the caller's org and produce identical aggregates per row. No legitimate cross-org aggregation happens in this view.

#### 2.3 `public.investor_return_metrics`
```sql
SELECT ic.id AS commitment_id, ic.org_id, ic.investor_id, i.investor_name,
       ic.entity_id, le.entity_name,
       ic.drawn_amount AS capital_invested,
       COALESCE(dt.total, 0) AS total_distributions,
       CASE WHEN ic.drawn_amount > 0 AND ad.annual_total IS NOT NULL
            THEN round(ad.annual_total / ic.drawn_amount * 100, 2)
            ELSE 0 END AS current_yield_pct,
       /* + IRR-style ratios and lifetime return % */
  FROM investor_commitments ic
  JOIN investors i ON i.id = ic.investor_id
  JOIN legal_entities le ON le.id = ic.entity_id
  LEFT JOIN LATERAL (...) dt  ON true
  LEFT JOIN LATERAL (...) ad  ON true
 WHERE ic.status IN ('active','fully_drawn');
```
**Recommendation: convert to SECURITY INVOKER.** Same reasoning as 2.1/2.2 — every base table has org RLS, no cross-org joins are required. The lateral subqueries on `investor_distributions` will be filtered correctly under invoker RLS.

#### 2.4 `public.portfolio_monthly_summary`
```sql
SELECT org_id, snapshot_month,
       count(DISTINCT property_id) AS property_count,
       sum(gross_rent_due)         AS total_rent_due,
       sum(gross_rent_received)    AS total_rent_received,
       sum(void_loss)              AS total_void_loss,
       sum(total_costs)            AS total_costs,
       sum(mortgage_payments)      AS total_mortgage_payments,
       sum(net_operating_income)   AS total_noi,
       sum(net_cash_flow)          AS total_cash_flow,
       CASE WHEN sum(gross_rent_due) > 0
            THEN round(sum(gross_rent_received)/sum(gross_rent_due)*100, 2)
            ELSE 0 END AS portfolio_collection_rate,
       round(avg(occupancy_rate), 2) AS avg_occupancy_rate,
       sum(valuation_at_snapshot)  AS total_valuation,
       sum(debt_at_snapshot)       AS total_debt,
       sum(equity_at_snapshot)     AS total_equity,

            ELSE NULL END AS portfolio_ltv
  FROM financial_snapshots fs
 GROUP BY org_id, snapshot_month
 ORDER BY snapshot_month DESC;
```
**Recommendation: convert to SECURITY INVOKER.** `financial_snapshots` already enforces org-scoped RLS. Aggregating per `(org_id, snapshot_month)` under invoker semantics naturally limits the result to the caller's org and produces correct totals — there is no need to bypass RLS.

**Summary**: All four views can safely be migrated to `WITH (security_invoker=on)` in a follow-up prompt; none of them appear to need cross-org access. **No view definitions changed in this audit.**

### Item 3 — `freeagent-oauth-callback` state token

**File reviewed**: `supabase/functions/freeagent-oauth-callback/index.ts`.

**State decoding (line 38)**:
```ts
const stateData = JSON.parse(atob(state));
const { entityId, companyId, orgId, userId, useSandbox, nonce } = stateData;
```

**Verdict: state is plain base64-encoded JSON. It is NOT HMAC-signed, has no embedded TTL, and the `nonce` field is read but never validated against any server-side store.**

**Mitigations currently in place** (lines 47–59):
- The `userId` claimed in the state is cross-checked against `memberships` to confirm the user is `owner` or `admin` in the claimed `org_id`.
- `entityId` and `companyId`, if present, are verified to belong to `orgId`.

**Why this is still weak**:
- An attacker who can guess or obtain a valid `(userId, orgId)` pair (e.g., from an exposed support log, an old shared link, or a leaked invite) can craft a state and stage a CSRF-style account hijack of the FreeAgent connection without needing to be that user.
- There is no replay protection — the same state can be used repeatedly until manually revoked.
- There is no expiry — a state captured months ago is still accepted.

**Recommendation (do NOT apply in this prompt — file a hardening prompt)**:

1. Sign the state on the client/edge with HMAC-SHA256 using a server-only secret (`FREEAGENT_STATE_SECRET`):
   ```ts
   const payload = { orgId, userId, entityId, companyId, useSandbox, nonce, exp: Date.now() + 10*60*1000 };
   const body = base64url(JSON.stringify(payload));
   const sig  = base64url(hmacSha256(STATE_SECRET, body));
   const state = `${body}.${sig}`;
   ```
2. In `freeagent-oauth-callback`, split on `.`, recompute the HMAC, **constant-time** compare, then check `payload.exp > Date.now()` (recommended TTL ≤ 10 minutes).
3. Persist `nonce` in a short-lived `oauth_states` table (or a Deno KV / Redis cache) with a uniqueness constraint and delete it on first successful use to prevent replay.
4. Keep the existing membership cross-check as defence-in-depth.

**Action**: file a follow-up prompt titled "Harden FreeAgent OAuth state with HMAC + replay protection". No code changes in this audit.
