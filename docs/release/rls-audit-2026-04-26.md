## Section C — Policies with `true` / true-equivalent expressions

The DB scan found **9** policies whose `USING` or `WITH CHECK` is literally `true`, `auth.uid() IS NOT NULL`, or `auth.role() IS NOT NULL`. Classification below.

### C.1 — Intentionally public / global reference reads — **leave as-is, add documenting comment**

| Table | Cmd | Policy | Expression | Rationale |
|---|---|---|---|---|
| `ai_extraction_templates` | SELECT | Authenticated read | `auth.uid() IS NOT NULL` | Global template library shared by all tenants. |
| `certificate_type_mappings` | SELECT | Authenticated users can read certificate type mappings | `true` | Global lookup table (cert-type → category). |
| `compliance_templates` | SELECT | Anyone authenticated can read templates | `auth.uid() IS NOT NULL` | Global compliance template catalogue. |
| `financial_categories` | SELECT | Authenticated users can read financial_categories | `auth.uid() IS NOT NULL` | Global chart-of-accounts seed data. |
| `demo_requests` | INSERT | Anyone can submit demo requests | `true` (with check) | Public marketing form; companion SELECT is admin-gated. |

➡️ **Action:** Add an `-- INTENTIONAL PUBLIC READ: <reason>` SQL comment above each policy in its source migration (or a follow-up doc-only migration) so future audits can skip them quickly. No behavioural change.

### C.2 — Service / system-write policies — **leave as-is, scope is service-role-only by convention**

| Table | Cmd | Policy | Expression | Notes |
|---|---|---|---|---|
| `audit_log` | INSERT | System can insert into audit_log | `WITH CHECK true` | Written by triggers / service role. SELECT side is correctly org-scoped. The PUBLIC role grant is fine because triggers run `SECURITY DEFINER`. Consider restricting to `TO service_role` for defence-in-depth. |
| `scheduled_email_runs` | INSERT | Service can insert email runs | `WITH CHECK true` | Written by cron / edge functions. Same defence-in-depth note. |
| `scheduled_email_runs` | UPDATE | Service can update email runs | `USING true` | Same as above. |

➡️ **Suggested hardening (optional, not required):**
```sql
-- Defence-in-depth: restrict service-only writes to the service_role grantee.
ALTER POLICY "System can insert into audit_log" ON public.audit_log TO service_role;
ALTER POLICY "Service can insert email runs"   ON public.scheduled_email_runs TO service_role;
ALTER POLICY "Service can update email runs"   ON public.scheduled_email_runs TO service_role;
```

### C.3 — Accidentally permissive — **tighten**

| Table | Cmd | Policy | Current | Risk |
|---|---|---|---|---|
| `notifications` | INSERT | Authenticated users can create notifications | `WITH CHECK (auth.uid() IS NOT NULL)` | Any authenticated user (including a tenant or shareholder portal user from a different org) can insert a row targeting any `user_id`. Spoofing / spam risk. |

➡️ **Proposed tightening (report-only — not applied):**
```sql
-- Restrict notification inserts: a user may only create a notification addressed to themselves.
DROP POLICY "Authenticated users can create notifications" ON public.notifications;

CREATE POLICY "Users can insert own notifications"
ON public.notifications
FOR INSERT
TO authenticated
WITH CHECK (
  user_id = auth.uid()
  -- system / cross-user notifications must go through SECURITY DEFINER fn or service_role
);

-- Allow service_role + SECURITY DEFINER triggers to bypass for system notifications:
CREATE POLICY "Service can insert system notifications"
ON public.notifications
FOR INSERT
TO service_role
WITH CHECK (true);
```

> No other `true`-equivalent policies in the database besides those listed above. The Supabase linter `SUPA_rls_policy_always_true` warnings (4 of them) all map to the rows in C.2 + C.3.

### Action items for edge functions

1. **`freeagent-oauth-callback`** — currently has no auth gate (expected for an OAuth callback) but the audit could not confirm the `state` value is HMAC-signed or replay-protected. **Action:** add an explicit `// PUBLIC: OAuth callback — security relies on signed state nonce + short TTL` comment, and verify in code review that the `state` token is HMAC-signed (not just base64-encoded JSON) and single-use. If it is only base64, that is a **NEEDS-HARDENING** item, not a NEEDS-AUTH one.
2. **`get-maps-key`** — the function name implies a public read but the implementation requires auth. Either rename to `get-maps-key-authed` or add a `// AUTH: requires session` comment to prevent future contributors from "fixing" it by removing the auth check.
3. No function in the audit was classified **NEEDS AUTH**.

## Section E — Recommended fix order (highest blast-radius first)

The items below are ordered by impact (rows × sensitivity × cross-tenant exposure). Only **#1** is a real cross-tenant data risk uncovered by this audit; the rest are defence-in-depth and hygiene.

| # | Area | Action | Blast radius | Effort |
|---|---|---|---|---|
| 1 | `notifications` INSERT policy (Section C.3) | Replace `auth.uid() IS NOT NULL` with `user_id = auth.uid()`; add a separate `service_role`-only policy for system notifications. | Cross-tenant spoofing of in-app alerts. | Low |
| 2 | `audit_log` + `scheduled_email_runs` service-write policies (C.2) | Restrict policies to `TO service_role` so PUBLIC-grant + `true` cannot be combined by future schema drift. | Defence-in-depth. | Low |
